## 1. 本專案定位與角色

### 1.1 專案扮演的角色

- 本專案是企業級 IdP 與 OAuth/OIDC 授權中心。
- 統一提供登入、授權、Token 發行與撤銷能力。
- 目標是讓各 Web 應用不再自行處理密碼與授權流程。

### 1.2 Web 應用的責任邊界

- Web 應用只需導向標準授權流程與驗證 Token。
- 功能授權以 Scope 與政策控制，不靠應用端硬編碼。
- 多系統可共用同一登入與授權治理機制。

---

## 2. 為什麼企業需要 OIDC/OAuth2

### 2.1 常見痛點

- 多系統各自登入，導致帳號治理不一致。
- 權限模型不統一，跨系統整合時容易超權或漏權。
- 每個系統重複建置驗證功能，成本高且安全品質不穩定。
- 發生資安事件時，缺乏統一稽核資料，調查效率低。

### 2.2 導入後可解決的管理問題

- 用標準協定統一身分驗證與授權流程。
- 降低重複開發與維運工作量。
- 讓新系統接入有標準流程，縮短時程。
- 提升風險可見性與治理能力。

## 3. OIDC/OAuth2 核心概念（白話 + 技術）

### 3.1 一句話區分

- OIDC：解決「我是誰」。
- OAuth2：解決「我可以做什麼」。

### 3.2 角色模型

- Resource Owner：資源擁有者，通常是使用者。
- Client：要存取資源的應用或服務。
- Authorization Server：負責登入、授權、發 Token。
- Resource Server：接收 Token 並提供 API。

### 3.3 Token 概念

- Access Token：短期憑證，供 API 授權檢查。
- Refresh Token：更新 Access Token，減少重登入。
- ID Token：OIDC 身分資訊封裝，供客戶端辨識登入者。

### 3.4 Scope 與 Claims

- Scope 是「可做什麼」的授權範圍。
- Claims 是「身分/屬性資訊」的聲明資料。
- 良好實務：Scope 盡量業務化且可治理；Claims 盡量最小化。

## 4. Web 應用如何接入本專案

### 4.1 使用者登入流程（高階）

- Web 應用導向統一登入與授權頁面。
- 使用者完成身分驗證與權限同意。
- 應用用授權碼交換 Token 後開始存取 API。

### 4.2 Web 應用的落地責任

- 不保存使用者密碼，只處理授權流程回傳結果。
- 以 Token 與 Scope 做權限判斷與功能控制。
- 依使用情境選擇短效 Access Token 與 Refresh 策略。

### 4.3 系統對系統整合

- 後端服務使用 Client Credentials 取得機器 Token。
- 以 Scope 限制服務可存取的資源範圍。
- 可搭配網段限制與配額控制降低濫用。

## 5. 主要授權流程與適用情境

### 5.1 Authorization Code + PKCE（本專案預設）

適用：Web、SPA、行動應用。

重點：

- 使用授權碼交換 Token，不直接暴露敏感憑證。
- PKCE 增加挑戰驗證，降低授權碼攔截風險。
- 可自然搭配使用者同意與細粒度授權提示。

### 5.2 Client Credentials（系統對系統）

適用：後端服務間整合。

重點：

- 不涉及人員登入，依賴客戶端身分信任。
- Token 應限制於最小 Scope，避免「全權 Token」。
- 建議搭配配額、網路邊界與輪替機制。

### 5.3 Refresh Token（會話延續）

適用：需要長會話但不能長效 Access Token 的情境。

重點：

- Access Token 短效化，Refresh Token 控制續期。
- 應考慮旋轉更新、撤銷、重放偵測。

### 5.4 Device Flow（受限輸入裝置）

適用：輸入能力有限的裝置。

重點：

- 將登入操作轉移到第二裝置完成。
- 需加強輪詢節流與過期策略。

## 7. 企業級架構設計重點

### 7.1 架構分層建議

- 協定層：處理授權端點、Token 發行、標準流程。
- 服務層：承接業務規則，例如權限映射、同意策略。
- 資料層：存放客戶端、Scope、同意、稽核與設定。
- 管理層：提供管理介面與治理流程。

### 7.2 可擴充設計

- 標準端點先行，客製行為以策略方式擴充。
- 身分來源與授權規則解耦，利於外部整合。
- 可觀測性預埋，避免事後補監控。

### 7.3 高可用與穩定性

- Token 驗證與簽章機制需可水平擴展。
- 關鍵設定集中管理，避免節點行為不一致。
- 錯誤處理與降級策略要先定義。

## 8. .NET / ASP.NET Core 落地藍圖

### 8.1 Pipeline 與責任邊界

- 驗證與授權中介流程要明確排序。
- 驗證（Authentication）與授權（Authorization）策略應拆開治理。
- 端點層只做協定轉譯，業務規則放服務層。

### 8.2 Policy-Based Authorization

- 以政策與需求規則控管 Scope、角色與條件。
- 策略命名可讀化，避免硬編碼判斷散落各處。
- 高風險 API 可附加條件，例如來源限制或高強度驗證。

### 8.3 設定與環境管理

- 分離環境設定、密鑰、憑證與功能開關。
- 配置變更需可審計、可回溯、可回滾。
- 建議建立一致的設定檢核清單。

### 8.4 資料與遷移策略

- 使用資料遷移管控 schema 演進。
- 保留初始化資料策略，確保環境一致。
- 對敏感欄位建立保護與存取審核規則。

## 9. 安全控制面（主管常問）

### 9.1 最小權限與權限治理

- 預設不授權，按需求開放。
- Scope 應可稽核、可審批、可追蹤。
- 權限變更要有流程與責任人。

### 9.2 身分強度與風險分級

- 高敏感操作啟用多因子驗證。
- 依場景要求不同驗證強度（一般查詢 vs 高風險操作）。
- 異常行為可觸發再驗證或拒絕存取。

### 9.3 常見攻擊防護

- CSRF：防跨站請求偽造。
- Replay：防止憑證重放。
- Brute Force：登入與授權端點節流。
- Token 洩漏：短時效、撤銷、監測告警。

### 9.4 稽核與合規

- 關鍵事件需記錄：登入、授權、拒絕、撤銷、設定變更。
- 稽核資料需可查詢、可關聯、可保存到指定年限。
- 事件分級與通報流程要事先約定。

## 10. 整合策略（給各應用團隊）

### 10.1 Web 應用

- 優先採 Authorization Code + PKCE。
- 會話管理與 Token 管理分離，避免混用風險。
- UI 端只持有必要資訊，不暴露敏感憑證。

### 10.2 SPA 與行動應用

- 嚴格使用 PKCE，不使用不安全舊流程。
- Token 儲存策略需符合裝置安全能力。
- 登入失效與重新授權體驗需一致。

### 10.3 後端與 API

- 使用機器 Token，避免共享使用者帳密。
- API 端做 Token 驗證與 Scope 檢查。
- 高價值 API 加入額外風險控制條件。

## 11. 測試、驗收與品質保證

### 11.1 測試分層

- 單元測試：驗證規則與授權邏輯。
- 整合測試：驗證端點、資料、策略協作。
- 端對端測試：驗證完整登入與授權情境。

### 11.2 必測情境

- 正常流程：登入、授權、換 Token、呼叫 API。
- 異常流程：過期、撤銷、錯誤 Scope、非法客戶端。
- 安全流程：暴力嘗試、重放、CSRF、同意頁繞過。

### 11.3 驗收指標範例

- 授權成功率與平均延遲。
- Token 相關錯誤率與修復時效。
- 新系統接入工時下降幅度。
- 高風險事件攔截與處置效率。

## 13. 主管常見問答（報告備答）

### Q1：這個計畫的核心價值是什麼？

答：把分散驗證收斂為企業共用能力，降低資安與維運風險，同時提升整合效率。

### Q2：會不會增加導入成本？

答：初期有建置成本，但可透過標準化降低後續每個系統的重複投入，整體長期成本下降。

### Q3：如果發生資安事件，是否可快速應對？

答：可透過 Token 撤銷、異常偵測與統一稽核機制做快速處置與追蹤。

### Q4：如何證明計畫成功？

答：以授權成功率、接入工時、風險事件處置效率等指標做量化驗收。

# Recovery Email Selection Schema Decision

Status: concrete persistence schema implemented; provider model/script checks and focused offline relational state tests passed. SQL Server/PostgreSQL database execution is unverified. This document does not claim deployed behavior.

## Context

Recovery destinations are account security state. The existing `RecoveryEmailRecord` is scoped to `LocalAccountId`, with a unique account index, user FK, and monotonically updated `Version` concurrency token. `RecoveryProofChallenge` references its recovery record and carries an explicit purpose, hashed proof material and context. Migration and native administrator approvals are distinct durable records. Replacing the record's address before verifying a candidate cannot preserve the previous effective destination.

The current self-service authorizer requires the authenticated account and MFA or hardware-key AMR, but does not independently enforce recency. Existing MFA enrollment reauthentication is purpose-specific. The existing mail queue is process memory; enqueue success cannot prove delivery or survive abrupt process loss.

## Decision

Use additive account-scoped state and matching SQL Server and PostgreSQL migrations. Preserve existing recovery-record identities, FKs, approval purposes and concurrency contracts. Introduce only the state needed for preference, pending change, selection epoch, durable precheck and reliable recovery notifications; reuse equivalent existing structures when their invariants are demonstrable. The state stage determines exact names, types, filters and relationships in both provider snapshots.

### Concrete schema and service contract

The SQL Server migration is `20260930095054_AddRecoveryEmailSelectionState`; the PostgreSQL migration is `20260930095106_AddRecoveryEmailSelectionState`. Each migration has its generated designer and updated provider snapshot. No existing row is updated, deleted or reclassified. `RecoveryEmails.Provenance` defaults to `LegacyUnknown`; existing IDs, addresses, verified dates and `Version` values survive. No preference backfill invents user intent. Absence of a preference means legacy interpretation, not an explicit request for default.

All six new entity types have numeric `Version` optimistic concurrency. User-owned new rows have account FKs. Pending-to-step-up, grant-to-provider-binding and grant-to-challenge relationships restrict deletion so an active dependency is not silently detached. Existing challenge-to-recovery-record and migration-continuation FKs retain their delete behavior. New default challenges have a null `RecoveryEmailId`; old rows keep their non-null values. Native approvals likewise allow a null address ID only through the explicit default factory. This avoids a redundant permanent default address row. Migration approvals already have no recovery-email FK and receive the same selection binding columns.

`RecoveryProofChallenge`, `RecoveryResetApproval` and `NativeRecoveryResetApproval` gain nullable `SelectionEpoch`, `DestinationKind`, `DestinationFingerprint` and `DestinationVersion`. Null means pre-feature state, never a wildcard when new selection enforcement is enabled. `BindSelection` binds once; `MatchesSelection` compares every component exactly. Existing constructors and purpose checks remain. `RecoveryProofChallenge.CreateForDefault` accepts native recovery or migration OTP with its required continuation; `NativeRecoveryResetApproval.CreateForDefault` takes the bound native challenge. No enrollment/custom provenance is created by these factories.

The existing `ProviderSubjectDirectoryBinding` has immutable ID, account, namespace, subject and directory object but no numeric Version. `ProviderBindingVersion` is a SHA-256 digest of an unambiguous length-delimited encoding of that exact tuple/ID/object, not a submitted identifier digest. Compare the current binding ID and recomputed digest at each ceremony stage. Do not normalize opaque tuple strings. This avoids truncating supplementary Unicode scalars into new wire-sized columns. The alias is mutable and is not an authority key. The service must define one canonical fingerprint encoding and share it across prepare/send/verify/reset. `EffectivePolicyVersion` and destination fingerprint are likewise bounded digests of their complete server-owned decisions, not browser data.

### Required transaction usage

These entities provide durable state and CAS tokens; they are not standalone authorization services. Caller checks still own current eligibility, policy, provider binding, account/security, fresh authority-correct step-up and cryptographic OTP verification.

1. Begin change validates fresh authorization and inserts a pending row without mutating active. `TryReserveResend` preserves expiry and attempt count, clears delivered state, and respects cooldown. `TryMarkDelivered` is called only after actual send success. Failed send revokes the pending request; its active destination remains unchanged.
2. Verify reserves an attempt, verifies the candidate code and fresh step-up, then uses one relational transaction for `TryConsume`, `RecoveryEmailRecord.ActivateVerifiedCustom`, preference `TrySelect`, proof invalidation and old/new notification insertion. Unique account indexes and Version/epoch CAS reject concurrent losers. A service must not persist a pending consume separately from this transition.
3. UseDefault resolves current trusted evidence before `TrySelect`. Source opt-out, administrative block and disabled semantics are independent; clearing one must not clear another. All effective changes increment the epoch. Cancel only calls pending `Revoke`.
4. Send creates a fully context/selection-bound challenge and calls grant `TryReserveChallenge`. Persist both in one relational transaction before SMTP. This sets challenge delivery to Reserved and consumes the grant exactly once. `TryCompleteDelivery` records Delivered or Failed; reserved/failed challenges reject verification and consumption. A crash before completion fails closed. Existing pre-feature challenges retain null delivery state for compatibility. Later checks retrieve the linked grant to revalidate its policy/provider binding; no service may treat provider Verified alone as reset permission.
5. Notification `TryClaim` is committed before dispatch and provides a bounded, expiring lease. Completion/failure must present the matching current lease. A crashed lease can be reclaimed only after expiry and within the persisted attempt budget. Delivery is at-least-once with possible duplicate notification after an SMTP-success/process-crash gap; it never claims exactly-once SMTP. Recipient/body logging remains prohibited. Services must bound batch sizes and remove expired intents only under their retention policy.
6. Throttle `TryTake` updates the shared CAS row. Concurrent insert conflicts or lost updates require a bounded reload/re-evaluation, never treating a failed save as accepted budget. Partition hashes must include the operation and budget dimension. This has no effect on `AccessFailedCount`.

`RecoveryStepUpGrant.TryConsume` compares account/security/browser/CSRF/authority and rejects future, expired, revoked or replayed proof. The current `Web.IdP/Helpers/MfaEnrollmentSession.cs` tracks a different purpose and even admits partial authentication for enrollment, so it cannot authorize recovery changes. The existing interactive sign-in path and `ServiceCollectionExtensions` application-cookie `OnSigningIn` callback show where trusted completion can be observed; the later web task must attach a separate pending recovery purpose and preserve correct Local/Directory/external routing. It must not mint grants on arbitrary cookie refresh or borrow enrollment proofs.

| State | Required semantics |
| --- | --- |
| Preference | Distinguish UseCustom, UseDefault, and explicit blocked/disabled semantics already supported; record provenance separately. Scope by LocalAccountId, never PersonId. |
| Active record | Remains the verified effective custom destination while a replacement is pending. Preserve existing identifier/FKs and Version concurrency behavior. |
| Pending change | Candidate address and existing safe normalization, OTP hash, expiry, attempt/cooldown, account/context, expected epoch/security state, consumed/revoked state. Never replace active before successful verification. |
| Selection epoch | Monotonic version changed by successful effective selection/address changes, revoke and use-default. Distinct from active record Version, which also changes for send reservations. |
| Precheck grant | Server-owned short-lived durable state binding account, exact provider binding/version, security stamp, browser/CSRF hashes, policy version, destination fingerprint/version and expiry/consume/revoke state. No submitted identity value or hash. |
| Recovery notification | Minimal durable intent created in the preference transition transaction, with bounded retry and restart-safe claiming/outcome state; reuse existing SMTP dispatcher. Include only data necessary to notify appropriate old/new destinations, excluding credentials, OTP, identity evidence and proof secrets. Avoid recipient/body logging and sanitize failures. |

Do not make a redundant permanent copy of provider default metadata merely to represent preference. Default evidence and custom enrollment are different authorities. A source-address OTP proves possession for the ceremony; it does not create UseCustom or promote source trust to locally verified custom.

## Destination and historical compatibility

An effective verified custom always takes precedence and does not require metadata availability for its selection. Pending first enrollment leaves an eligible default effective; pending replacement leaves the old custom effective. Failure, expiry, cancellation and send failure preserve active selection. An unavailable, corrupt, revoked or unsuccessfully delivered custom fails closed without default fallback. A lookup exception is not evidence that custom is absent.

UseDefault resolves only explicitly trusted, fresh, eligible and unrevoked evidence under source-origin acceptance policy. Contact email alone is never proof. Persistent trusted-default selection is independently opt-in and defaults disabled; it does not relax current-period freshness, future-time rejection, source conflict, local lifecycle or revocation rules.

Verified legacy addresses whose provenance cannot be proven retain their effective precedence as LegacyUnknown; do not call them user-chosen custom or provider default without evidence. Anonymous recovery cannot reclassify them. Preserve source bootstrap revocation as a default blocking signal independently from custom availability and administrative disablement. Ambiguous historical disablement fails closed and requires an explicit cleanup decision. Re-enabling source opt-out and overriding administrative disablement require their respective authorization.

Account A's change never modifies account B, even for a shared Person. Login email, Person email, MFA email, upstream metadata and directory mail stay separate.

## Atomic transitions and purpose compatibility

Administrative replacement reuses an existing account-scoped custom record even when a default-backed challenge has no recovery-email ID. Authorized legacy removal with RIV enabled retains consumed precheck grants and their reserved challenges: revoke the challenge and detach its email reference before deleting the address. These changes and the source-bootstrap revocation marker are saved atomically; retained challenge metadata never grants new recovery authority.

Begin/replace pending records only the candidate. Resend preserves the maximum attempt budget and cannot indefinitely extend expiry. VerifyChange requires fresh trusted account authorization and candidate OTP, then atomically consumes pending, updates verified active custom, selects UseCustom, increments epoch and invalidates old grants/challenges/approvals exactly once. CancelPending affects only that account's pending record.

UseDefault is a separate sensitive operation: fresh step-up, re-resolution of current eligible default and confirmation bound to its masked destination precede an atomic preference/epoch transition. Missing default cannot be reported as restored recovery. Revoke/disable remains a separate operation.

SendOtp atomically consumes one durable precheck grant and reserves one challenge across instances. SMTP runs outside that transaction; failure leaves the reservation unredeemable and never changes recipient. ReadyToSend requires explicit send. With `ForgotPasswordRecovery.PrecheckHintsEnabled=true` (the default), eligible guidance includes only the masked destination. With it false, comparable valid prechecks expose the same public phase/action without eligibility or a mask, also during GET restoration and after Send. An OFF-mode server-session phase marker is presentation state only: it creates no grant or challenge, and unavailable Send still follows the existing denial path. Precheck sends no mail in either mode. Request IDs and provider Verified responses cannot substitute for grants, OTP, reset proof or an authenticated session. Every later stage rechecks current destination, epoch, authority, account/binding/security and policy state; a changed default invalidates context instead of silently rerouting.

Existing migration/admin purposes remain independently authorized, cannot exchange proofs with address change or anonymous reset, and retain FK compatibility. Required provider cohorts fail closed on missing binding. Preserve existing Local password policy/history/session/token revocation and Directory pending/uncertain-write barriers.

## Fresh authorization and operational consequences

Preference mutation retains own-account full authentication and the existing MFA/hardware-key prerequisite, plus recent trusted reauthentication (default five-minute window). Bind recovery-specific proof to account, purpose, context and security state; old AMR and LastLoginDate alone are insufficient. Partial login, migration continuation and required-password-change sessions cannot mutate recovery state. Candidate email OTP is not step-up. Route reauthentication through the current correct Local/Directory/external authority without retrying credentials against another provider; unavailable prerequisites use existing enrollment or administrator assistance.

Notification persistence is narrowly recovery-specific; do not rewrite site messaging. Shared throttles are separate from ordinary login AccessFailedCount. Generic in-process queue and rate limiter behavior do not demonstrate cross-instance safety.

Both provider upgrades must preserve existing addresses/challenges/approvals/tombstones. Do not allow old and new recovery writers concurrently. Flags default disabled. Application rollback retains effective custom preference, revocations and pending audit; disabling selection cannot change custom into default. Schema downgrade has separate data-preservation and old-binary compatibility gates, and is never an automatic production operation.

Both `Down` migrations start with a provider-specific refusal when any new state row, non-LegacyUnknown provenance, selection-bound proof/approval, or null default-address FK exists. They never synthesize zero GUIDs or silently drop effective preference/tombstones. A schema-only rollback with no newly used state may remove the added schema and restore non-null IDs. Once used, downgrade requires a separately authorized archival and compatibility decision; normal application rollback retains the schema. Maintenance must stop all old/new recovery writers together during rollout or rollback.
